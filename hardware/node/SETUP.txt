HIP AND WRIST: FIXED PRESETS, NO STANDSTILL OR CALIBRATION REPS

Hardware: FireBeetle ESP32 (ESP32-WROOM-32D), each with its MPU6050.
PlatformIO environments (native ESP-IDF):
  node1_private_tls = HIP       Bluetooth name: ExerciseHip
  node2_private_tls = WRIST     Bluetooth name: ExerciseWrist
The environment names do not configure TLS; communication is Bluetooth + ESP-NOW.

Both use hardware/main.cpp and the shared code in hardware/node. MAC addresses and
shared settings are in ExerciseConfig.h. Fixed limits and board assignments
are in ExercisePresets.h. Upload BOTH boards when updating the shared firmware.

PLATFORMIO SETUP AND UPLOAD

1. Open the repository folder in VS Code with the PlatformIO extension.
2. Use the existing platformio.ini: espressif32@7.1.0, firebeetle32, espidf.
   The native MPU6050 driver does not require Arduino or Adafruit libraries.
3. In PlatformIO Project Tasks, build node1_private_tls and node2_private_tls.
   Fresh configurations use size optimization from sdkconfig.defaults. If an
   existing sdkconfig.node* still selects debug optimization and linking reports
   IRAM overflow, run `pio run -e <environment> -t menuconfig`, select Compiler
   options -> Optimization Level -> Size, save, and rebuild that environment.
4. Connect the hip over USB and upload using node1_private_tls.
   Connect the wrist over USB and upload using node2_private_tls.
   Upload over USB, not the Bluetooth serial port. If unsure which COM port is
   which, connect one board at a time. Do not open the same port in two monitors.
5. Open each PlatformIO serial monitor at 115200 baud. The existing configuration
   sends commands with LF when you press Enter.
   Check the role, Wi-Fi STA MAC, ESP-NOW status, Bluetooth name and STANDBY.
   Compare printed STA MACs against HIP_MAC/WRIST_MAC in ExerciseConfig.h.
   If different, edit the addresses and upload BOTH environments again.
   Use Wi-Fi STA MAC addresses, not Bluetooth MACs. Both use the same channel.
   If MPU6050 is not found, check the existing sensor wiring before continuing.

Windows build paths: if compilation reports "invalid argument 'C:/uni' to
'-fmacro-prefix-map'", build a copy of the project from a folder without spaces
(for example C:/projects/CG4002). The short-path helper does not cover all paths
generated by ESP-IDF/PlatformIO. This is a build-path issue, before compilation
of the firmware logic.

HOW THE CONNECTIONS WORK

Laptop <-> ExerciseHip: USB or Bluetooth commands and hip telemetry.
Laptop <-> ExerciseWrist: USB or Bluetooth commands and wrist telemetry.
Hip <-> Wrist: ESP-NOW activation handover, mode synchronization and LED events.

No Wi-Fi router or Bluetooth pairing between the boards is needed.
Each monitor shows only its own board. Counts and exercise selection are not
forwarded. Both boards must be powered for a new activation: the other board
must acknowledge standby. Bluetooth pairing alone does not activate counting.

LOCAL SENSOR HISTORY (STEP 2, BEFORE COMMS INTEGRATION)

Both HIP and WRIST continuously retain successful MPU6050 reads, including while
their counters are in standby or waiting for activation. Each sample contains
local uptime in milliseconds (timestamped at read start), acceleration XYZ in
m/s2 including gravity, and gyro XYZ in rad/s. Values are saved before exercise
filtering or gyro correction. Failed reads do not insert zero or stale samples.

SensorHistoryConfig in SensorHistory.h sets a 5000 ms window and 8000 ms retention.
At the configured 50 Hz this uses 401 ring slots, about 11 KB. The manual window
command has a separate static scratch snapshot of the same size; neither array
uses the main task stack. Data is in RAM only and is lost on reboot. ACTIVATE,
STANDBY, RESET, exercise changes and mode changes preserve this history and the
sampling cadence. Generic peak detection is described below; automatic window
transmission is not implemented yet.

Bench inspection, on each board's USB or Bluetooth serial monitor:
1. Send BUFFER after boot. It reports the node, stored sample count, oldest/newest
   timestamps, covered span and newest sample age (all times in milliseconds).
2. Send WINDOW before five seconds of samples are available. Expect EMPTY or
   INSUFFICIENT_HISTORY. No samples are padded or invented.
3. After at least five seconds of successful sampling, send WINDOW again. It
   copies [latest sample time - 5000, latest sample time] and prints a summary.
   READY means enough history with no gap greater than 40 ms. SAMPLE_GAP means
   the actual samples were copied, but at least one interval/edge gap exceeds
   40 ms. max_gap_ms reports the largest gap; smaller jitter is not resampled.
   At exactly 50 Hz with both endpoints included, there are 251 samples. With
   real timing jitter or a t0 between samples, counts/endpoints can differ.
4. To simulate a delayed trigger, note newest_ms from BUFFER and send
   WINDOW:<that timestamp>, for example WINDOW:12000. This selects [7000,12000]
   regardless of when the command arrives, provided those times are retained.
   At nominal cadence, the extra history allows up to three seconds of delay,
   shared between peak confirmation and any later trigger/transport handling.
   END_NOT_AVAILABLE means t0 is newer than the last successful sample.
   INSUFFICIENT_HISTORY means the requested history is unavailable/expired.
5. RESET or change the exercise, then repeat WINDOW. The history should remain.
   Repeat in standby on each board; no peer connection is required for buffering.

WINDOW prints metadata only, avoiding a large serial dump that could delay the
sampling loop. It does not start counting, send ESP-NOW triggers, or send samples
to Ultra96. WINDOW without a timestamp anchors to the latest successful sample;
check BUFFER's age_ms to spot stale data after sensor failures.

For later integration, ExerciseNode::copySensorWindow(t0, destination, capacity)
copies samples in chronological order. Call it from the same main loop as update().
The caller owns the copy; subsequent ring writes cannot change it. OUTPUT_TOO_SMALL
reports the required count without writing a partial result. The local scheduler
below uses this same extraction behaviour. Transport and clock synchronization
are not implemented yet.
Timestamps are local to each board and wrap modulo 2^32 milliseconds; comparisons
assume timestamps less than 2^31 ms apart. Reboot starts a new local time reference.

GENERIC MOVEMENT PEAKS (STEP 3, BEFORE COMMS INTEGRATION)

Both nodes detect movement independently, including standby, failed activation
and active counting. No exercise selection or standstill calibration is needed.
The detector does not recognize an exercise, validate a rep, activate counting,
change LEDs, send peer trigger packets or transmit sensor windows to Ultra96.
Walking, handling the board and other non-exercise motion may also trigger it.

GenericPeakDetector.h contains provisional, shared movement thresholds, separate
from ExercisePresets.h. Tune them with recordings from the actual wearer/mounting:
  Acceleration gate: abs(|acceleration XYZ| - 9.81) >= 0.50 m/s2.
  Rotation gate: |gyro XYZ| >= 0.60 rad/s, assuming zero gyro bias.
Either channel can trigger, including rotation with little acceleration change.
A three-sample median filter rejects isolated spikes. The larger of the two
normalized signals must remain above its gate for at least 60 ms. A peak is
confirmed once the score falls at least 25% from its maximum for at least 40 ms.
The filtered peak can lag the raw sensor maximum by a sample; t0 is the timestamp
of the highest filtered score, not the later time at which the decline confirms it.
On a flat maximum, the first sample at that maximum supplies t0.

After a confirmed peak, both filtered signals must drop below 45% of their gates
for 80 ms to rearm. New excursions during the one-second trigger cooldown are
ignored until the signals settle again. This is trigger debounce during motion,
not a three-second startup wait. Sustained motion may produce only one trigger;
the local window session continues independently of subsequent peaks.
Candidates older than 2500 ms are discarded. Invalid values or sample gaps over
100 ms discard the partial peak/filter state, without removing the cooldown.
Counter RESET, exercise/mode changes and activation preserve the detector state.

Bench inspection, with either node powered and its serial monitor open:
1. Leave counting in standby. Small sensor noise should not print PEAK events.
2. Move the board through an acceleration or rotation peak. A confirmed movement
   automatically prints metadata such as:
     [PEAK | HIP | t0_ms=8240 | confirmed_ms=8340 | accel=1.60 m/s2 | gyro=0.10 rad/s]
   This is a USB/Bluetooth diagnostic line, not a comms packet or a sensor window.
3. Send WINDOW:8240 using the actual printed t0, promptly enough to retain its
   history. Expect READY when five seconds of healthy samples cover that time.
   The returned end time is t0, not confirmed_ms or the time the command arrived.
4. A peak during the first five seconds is still detected, but WINDOW can report
   INSUFFICIENT_HISTORY. No missing pre-boot samples are invented. Waiting for
   initial history does not require the wearer to stand still.
5. Repeat on WRIST, including rotation resembling jumping-jack arm movement.
   Verify that standby counts remain inactive and peaks cause no LED feedback.
   Try walking too: triggers are possible; exercise recognition belongs to comms.

The local scheduler receives each fresh peak directly. consumeGenericPeak(event)
remains an optional diagnostic observer: it returns the first unconsumed event
once without consuming a prepared window or resetting detector cooldown. Later
peaks are logged without replacing that pending observation. Reboot clears it.
Do not use this diagnostic observer to drive a second window scheduler.

LOCAL SLIDING WINDOWS (STEP 4, BEFORE COMMS INTEGRATION)

Each node starts ARMED. Its first local generic peak starts its own window session.
Sequence 0 is copied immediately when the peak is confirmed, before diagnostic
output: [t0 - 5000, t0]. Following endpoints are t0 + 1000, t0 + 2000, etc.
Each window is still five seconds long. Later peaks do not restart the timeline.
No further peaks are needed for windows to continue. HIP and WRIST are independent
here; a peak on one does not yet start the other. Timestamps are still local.

Windows use actual samples, including both endpoints when present. At exactly
50 Hz that is 251 samples; no padding, interpolation or fixed-size resampling is
performed. If t0 falls between samples, each copied sample stays within the
requested interval. Endpoint times remain on the t0-based grid despite loop jitter.
The scheduler waits up to 100 ms for a successful read to cover a due endpoint;
after that it records END_NOT_AVAILABLE/EMPTY rather than waiting indefinitely.
It runs even when reads fail or the main loop is between scheduled sensor reads.

An early peak still starts a session at its original t0. Its first windows may
report EMPTY/INSUFFICIENT_HISTORY with no sample payload. Later windows become
usable once enough history exists, without requiring a new peak. SAMPLE_GAP
includes real samples with a gap flag. Consumers must check each window's status.
If the loop stalls, at most the three most recent due slots are caught up, one
per update; older slots increment skipped. Sequence numbers retain their original
positions, so missing windows remain visible. The cadence never shifts to now.

There is a FIFO queue of three snapshots (about 21 KB), in addition to the 11 KB
history ring and 7 KB shared diagnostic scratch. All large arrays are static.
Each snapshot holds 252 samples at the configured 50 Hz: 251 inclusive samples
plus one for boundary timing jitter. If an interval exceeds that capacity, its
record reports OUTPUT_TOO_SMALL with no payload; samples are never truncated.
New ring samples cannot change queued/copied snapshots. A full queue preserves
its existing windows, including sequence 0, and drops each new due window with
QUEUE_FULL and an incremented dropped counter. Sampling/counting continue.
There is no comms consumer yet, so unattended testing fills the queue after three
records. STREAM:NEXT removes one record for bench inspection; it prints metadata
only. Future comms must consume the queue regularly. This is not lossless storage.
USB diagnostics have a 2 KB transmit buffer to reduce normal logging delays;
excessive output can still block if that buffer fills.

Commands (USB or Bluetooth, one command per line):
  STREAM                  Show ARMED/RUNNING/STOPPED, session/t0, queue and loss counts.
  STREAM:STOP             Stop preparation, clear the queue, disable automatic start.
  STREAM:ARM              Wait for the next fresh peak if stopped. A running session
                          keeps its current anchor. Does not reset the peak detector.
  STREAM:START            Start now using the latest sample timestamp, without a peak.
  STREAM:START:<t0_ms>    Start from a supplied past/current local timestamp. A future
                          t0 or an already-running session is rejected unchanged.
  STREAM:NEXT             Copy/remove the oldest queued record and print its summary.
                          This is a diagnostic consumer, not transmission to Ultra96.

There is no automatic inactivity timeout yet: preparation continues until STOP.
Counter ACTIVATE, STANDBY, RESET, exercise/mode changes and peer LED events do not
stop or restart the window session. STREAM controls do not activate/stop counting.
STOP preserves the sensor history; START begins a new local session with sequence
zero. ARM requires a new peak rather than replaying a previous pending observation.
Reboot clears everything and returns to ARMED. Session numbers are local to a boot.

Typical automatic output after a peak (example values, exact cadence assumed):
  [PEAK | HIP | t0_ms=8240 | confirmed_ms=8340 | accel=1.60 m/s2 | gyro=0.10 rad/s]
  [STREAM | HIP | RUNNING | session=1 | t0_ms=8240 | next_end_ms=9240 | queue=1 | dropped=0 | skipped=0 | local_only]
  [FRAME | HIP | session=1 | seq=0 | READY | start_ms=3240 | end_ms=8240 | samples=251 | queue=1 | dropped=0 | skipped=0]
  [FRAME | HIP | session=1 | seq=1 | READY | start_ms=4240 | end_ms=9240 | samples=251 | queue=2 | dropped=0 | skipped=0]
FRAME means prepared locally, never sent. FRAME TAKEN means removed by STREAM:NEXT.
If the queue fills, expect QUEUE_FULL on following intervals until records are taken.

Bench check on each board independently:
1. Power the node and leave counting in standby. STREAM should report ARMED.
2. Allow at least five seconds of samples, then move through a peak. Expect seq=0
   and then a window attempt each second, even if you stop moving.
3. STREAM:NEXT displays/removes the oldest snapshot. Repeat about once per second
   to emulate a consumer; otherwise observe queue=3 followed by QUEUE_FULL.
4. STREAM:STOP clears the queue. Further peaks are still logged but cannot start
   windows until STREAM:ARM or an explicit STREAM:START.
5. Test STREAM:START without movement. Stop before trying another anchor/session.
6. Counter reset/exercise changes should preserve the current t0 and sequence.

Integration hooks in ExerciseNode.h (same main loop as update(), never a radio callback):
  startWindowStream(t0) / stopWindowStream() / armWindowStream()
  windowStreamStatus()
  takeSensorWindow(destination)
Allocate the ScheduledWindow destination statically/on the heap on ESP32, not on
the main task stack. takeSensorWindow returns false without changing the output
when empty. On true it copies and removes exactly one record; the caller owns it.
Only samples[0 .. info.window.count) is valid, and only if window.copied() is true.
SAMPLE_GAP still needs the consumer's policy; unavailable-history records have no
sample payload. Taking is not an acknowledgement of delivery; a future transport
must retain its own copy if it needs retries. The manual NEXT command consumes
the same queue, so do not use it alongside the real comms consumer.

The remaining steps add shared trigger/clock coordination and actual comms
transport/feedback. No port is opened and no sensor payload is transmitted here.

WIRELESS MONITORS ON WINDOWS

1. Power both boards. Pair ExerciseHip and ExerciseWrist in Windows Bluetooth
   settings. Remove stale ExerciseNode pairings if necessary.
2. Find each device's outgoing Bluetooth serial COM port in Bluetooth settings
   (More Bluetooth settings -> COM Ports) or inspect Device Manager.
3. Open a separate PlatformIO serial monitor for each outgoing port, e.g.:
     pio device monitor --port COM7 --baud 115200
   Replace COM7 with the correct outgoing Bluetooth port for each board.
4. The USB COM port and Bluetooth COM port are different. Switch to the
   Bluetooth ports for wireless commands/telemetry; upload firmware via USB.
5. Keep battery power connected when removing USB. If a board reboots, it returns
   to standby. If no Bluetooth COM port appears, use USB monitors first and check
   Windows pairing/SPP serial-port availability. Commands work identically on USB.

EXERCISE ASSIGNMENTS AND AUTOMATIC MODES

  Board   Exercise       Automatic default mode
  HIP     SQUAT          PAUSE
  HIP     LUNGE          PAUSE
  HIP     PUSHUP         PAUSE
  HIP     LEG_RAISE      PAUSE
  WRIST   SITUP          PAUSE
  WRIST   JUMPING_JACK   CONTINUOUS

Selecting a different exercise automatically selects its default mode. Wrong-board
selections are rejected without disturbing the session. MODE commands are optional
overrides for testing, accepted only while active. These defaults and presets need
testing with the actual wearer; they do not recognize exercise form.

STEP-BY-STEP EXERCISE SESSION

Send each command on its own line. No MODE command is needed for normal use.
Selecting while inactive queues the exercise's mode; ACTIVATE applies and
synchronizes it after the other board acknowledges standby.

1. Squats on HIP, using the ExerciseHip monitor:
     EXERCISE:SQUAT
     ACTIVATE
   Wait for "Hip active; wrist acknowledged standby" and "Mode synced: PAUSE".
   The squat preset loads immediately after the standby ACK; no positioning
   movement, three-second standstill or calibration reps are required.
   Both LEDs blink three times without delaying sampling or counting.
   Begin squats; return to the starting
   position and pause briefly (at least about 0.35 seconds) between reps.
   Watch "COUNTING | Reps: ...". Each accepted rep flashes both LEDs once.

2. Switch to lunges on HIP:
     EXERCISE:LUNGE
   The hip stays active, zeros reps and immediately loads the lunge preset.
   Begin lunges without another standstill; ready blinks are nonblocking.
   PUSHUP and LEG_RAISE use this same procedure on HIP; PAUSE is automatic.

3. Switch to jumping jacks on WRIST, using the ExerciseWrist monitor:
     EXERCISE:JUMPING_JACK
     ACTIVATE
   Wait for "Wrist active; hip acknowledged standby" and "Mode synced: CONTINUOUS".
   Start jumping jacks immediately. "FINDING AXIS" is normal initially;
   move steadily until output becomes "COUNTING". Initial axis-discovery movement
   may not count; there is no additional two-rep calibration phase.

4. Switch to sit-ups on WRIST:
     EXERCISE:SITUP
   PAUSE is selected automatically. The preset loads immediately and mode sync
   runs in parallel. Exercise and mode change cause one counter restart.
   Keep the wrist in a consistent position relative to your torso during sit-ups.
   Perform reps with a brief pause between each; no startup standstill is needed.

5. New set of the same exercise: send RESET on the active board, then begin
   moving immediately. Stop counting with STANDBY on the active board.
   Closing a monitor does NOT stop counting.

After switching back to HIP, select its exercise and activate it. Each board
remembers its own selected mode, separately from the active peer's synchronized
mode, so a handover restores the correct local choice. Exercise is not forwarded.
After reboot HIP defaults to SQUAT/PAUSE and WRIST to JUMPING_JACK/CONTINUOUS,
both in standby. Standby telemetry and STATUS show the mode for next activation.

Optional override: while active, send MODE:CONTINUOUS or MODE:PAUSE. The override
persists through RESET, standby and handovers until a DIFFERENT exercise is
selected or the board reboots. Repeating the current EXERCISE command only shows
status; it preserves the count and override. To restore its default immediately,
send the corresponding MODE command while active.

COMMAND REFERENCE (USB OR BLUETOOTH)

ACTIVATE
  Request that the other board stop counting. After its standby ACK, this board
  becomes active, applies/synchronizes its selected mode and loads its preset
  with zero reps and no standstill. An already-active board keeps its session;
  use RESET for a new set. The peer acknowledgement is still required.
STANDBY (DEACTIVATE is an alias)
  Stop this board's counting and cancel pending activation. Bluetooth, ESP-NOW
  commands, sensor history and hip fall monitoring remain available.
RESET
  Clear reps. If active, immediately reload the fixed preset. If inactive,
  stay inactive. Cancel pending activation. No preset values are erased.
EXERCISE:<name>
  Select a permitted exercise on this board. Plurals/spaces/hyphens are accepted,
  e.g. EXERCISE:leg raises. A different selection loads its default mode, zeros reps
  and restarts counting once if active; standby stays standby and remembers the
  mode until activation. Pending activation is cancelled. Selecting the same
  exercise only shows status; it does not reset the count or manual override.
EXERCISES
  List this board's exercises and indicate which belong to the other board.
MODE:PAUSE / MODE:CONTINUOUS (PAUSE / CONTINUOUS also accepted)
  Optional override, accepted locally only on the active board; synchronized to
  the peer via ESP-NOW. It changes this exercise's selected mode until another
  exercise is selected or the board reboots.
  An actual mode change restarts each session, preserving active/standby state,
  and cancels pending activation. Repeating the same mode retries synchronization
  without resetting counts. Wait for "Mode synced". On timeout the local change
  remains; check peer power and resend the mode. PAUSE is a counting algorithm,
  not a standby command. A standby board accepts synchronized mode changes, but
  they never overwrite its own selected mode for next activation.
STATUS / HELP
  Show activation/radio status and exercise/mode/preset, or the command list.
  "ESP-NOW configured and ready" does not prove that the peer is currently online.
BUFFER
  Show local sensor history size, timestamps, span and age; counting is unchanged.
WINDOW / WINDOW:<t0_ms>
  Copy and summarize the inclusive five-second window ending at the latest sample
  or the supplied local unsigned 32-bit timestamp. See LOCAL SENSOR HISTORY above.
STREAM / STREAM:START[:t0_ms] / STREAM:STOP / STREAM:ARM / STREAM:NEXT
  Control or inspect local window preparation independently of counting. See
  LOCAL SLIDING WINDOWS for queue behaviour, diagnostic consumption and limitations.

FIXED PRESETS

Edit ExercisePresets.h to tune values, then upload both environments. Presets are
compiled into firmware and survive power loss. RESET reloads them. The node does
not learn RAM profiles or write profiles to flash in this preset workflow.

Pause mode: acceleration-magnitude deviation from nominal gravity (9.81 m/s2).
  Exercise       Board   Start (m/s2)  End (m/s2)  Peak (m/s2)  Time (ms)
  PUSHUP         HIP     0.50          0.20        0.70         700-6000
  SITUP          WRIST   0.50          0.20        0.70         700-6000
  SQUAT          HIP     0.80          0.30        1.00         700-6000
  LUNGE          HIP     0.80          0.30        1.00         700-6000
  LEG_RAISE      HIP     0.50          0.20        0.70         700-6000
  JUMPING_JACK   WRIST   0.50          0.20        0.70         700-6000

Squat/lunge reuse historical squat calibration gates as counting limits.
Push-up uses provisional old chest settings at the new hip placement. Sit-up,
leg-raise and jumping-jack values are mocks. These are not measured final profiles.
Pause durations include the finishing pause. This detector counts motion bursts;
compare its output against full physical reps while tuning.

Continuous mode has separately editable MOCK gyro limits for every exercise:
start 0.60 rad/s, end 0.18 rad/s, peak 0.70 rad/s, minimum angular travel 0.60 rad
in EACH direction, full-cycle duration 600-6000 ms. Axis and initial direction
are discovered each session. One-second axis windows may take longer with weak
or mixed motion. Acceleration thresholds cannot substitute for gyro limits.

Activation, RESET, exercise changes and mode changes use fixed sensor references:
GeneralConfig::GRAVITY_MPS2 = 9.81 m/s2 and GYRO_BIAS_RAD_S = {0, 0, 0} rad/s.
No new sensor baseline or gyro offset is measured. These are nominal assumptions,
separate from exercise thresholds. Actual sensor offsets can cause missed/extra
counts; test with the wearer/mounting before relying on these defaults.
Counting starts from zero after activation; earlier movement is not replayed.
Continuous mode still discovers its axis/direction from movement each session.
Wrist sit-ups need consistent arm position relative to the torso.

MIRRORED LED FEEDBACK AND RADIO BEHAVIOR

Both LEDs blink three times when an active session loads its preset: 100 ms OFF,
then 100 ms ON, repeated three times. Counting and axis discovery run during the
blinks; a rep flash can replace the ready pattern. Each counted rep flashes both
LEDs for 200 ms.
The standby board mirrors LEDs while keeping its own counter inactive.

Timers are nonblocking. LED packets are best effort with no ACK/retry. Wireless
delay means approximate synchronization; lost packets can miss flashes. Local
counting never depends on LED delivery. Session/sequence checks ignore duplicate
or stale events. Reset, exercise/mode changes and standby clear feedback.

ESP-NOW uses 24-byte version-4 activation, mode and LED packets. There are no sensor
streams, forwarded counts, remote fall messages, discovery broadcasts or heartbeats.
Activation and mode sync try five times at 500 ms intervals (2.5-second deadline).
No activation ACK means activation fails. If every ACK is lost, both may remain
in standby. HIP wins simultaneous pending requests. A delayed deactivation may
conservatively stop a board but cannot start it.

Once active, a board counts locally even if the other loses power/radio reception.
After a standby-board reboot, switch activation away and back to establish a new
LED session. ACTIVATE on an already-active board does not repeat the handshake.
After either board reboots, resend the desired MODE from the active board to sync.
Both Bluetooth and ESP-NOW share the ESP32 radio; test switching on real boards.

BENCH AND WEARABLE CHECKS

- Verify both USB and Bluetooth monitors accept STATUS and show STANDBY on boot.
- Alternate ACTIVATE; only the acknowledged requester counts.
- Reject SITUP on HIP and SQUAT on WRIST without changing the current session.
- With peer power off, a new activation must fail explicitly.
- Reject a local mode command on standby; synchronize mode from the active board.
- Select JUMPING_JACK while WRIST is inactive and HIP is in PAUSE. Activate WRIST:
  CONTINUOUS should load/sync automatically, with no manual MODE command.
- Change active WRIST to SITUP: PAUSE should load and counting restart once.
- Override its mode, hand activation away/back: the override should survive.
- Change to a different exercise: its default replaces the previous override.
- HIP/SQUAT/PAUSE: move immediately after activation; first valid rep counts as 1.
- Verify LUNGE, PUSHUP and LEG_RAISE on HIP; SITUP on WRIST.
- WRIST/JUMPING_JACK/CONTINUOUS: find axis, then count without calibration reps.
- RESET/exercise/mode changes clear counts and reload presets without standstill.
- No "Hold still" or "Move into your starting position" prompt should appear.
- Reboot returns defaults/standby; fixed presets remain available after activation.
- STANDBY stops counting; hip fall monitoring remains running.
- BUFFER/WINDOW work in standby on both boards, even when the peer is offline.
- Counter RESET/exercise changes preserve history; only reboot clears it.
- PEAK diagnostics appear on either board in standby without activating counting.
- The first peak starts that board's local window timeline; later peaks preserve t0.
- STREAM:STOP clears/disables the window queue; STREAM:ARM waits for a new peak.
- With no consumer, queue=3/QUEUE_FULL must appear while sensor sampling continues.
- Verify generic trigger sensitivity on the worn sensors, including walking/noise.
- Compare counts/LEDs against full physical reps; mocks require tuning.
