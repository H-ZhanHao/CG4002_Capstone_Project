COMMS REP COUNTS (hw-update)

Firmware counts exclusively from AR totals forwarded by comms. Sensor movement
never increments reps. LocalRepCounting.cpp preserves the old filtering and
RepCounter/ContinuousCounter integration for bench tests; all three source files
are excluded from hardware/CMakeLists.txt. There is no runtime local-count mode.
Sensor sampling, history, generic peak detection, window preparation and HIP fall
monitoring continue. Generic PEAK messages trigger windows, not rep increments.

CONNECTION AND COMMANDS

Comms connects to ExerciseHip or ExerciseWrist via Bluetooth Classic SPP. USB
accepts the identical commands for bench testing. Send ASCII lines ending in LF
(\n); CRLF is also accepted. Route results to the active board's connection.
No external comms/AR application is included in this repository.

1. Power both boards with the updated firmware and their configured peer MACs.
2. On the desired board select its exercise, then send ACTIVATE.
3. Wait for successful activation; the other board must acknowledge standby.
4. Send REPS (or STATUS) and read the HW-issued ticket, for example:
     [REPS | HIP | boot=12345 | session=2 | total=0 | WAIT_COMMS]
5. Comms sends the AR cumulative total using that exact boot/session:
     REPS:12345:2:5
6. Both the USB monitor and connected Bluetooth client receive:
     [REPS ACK | HIP | boot=12345 | session=2 | total=5 | ACCEPTED]
   Periodic telemetry shows:
     ... | COUNTING | Reps: 5 | Rep source: COMMS

The numbers above are examples: always read the actual ticket. Use the USB
monitor at 115200 baud with Newline selected, or monitor-serial.ps1 -Port COMx.
STATUS includes the latest total/ticket. REPS queries only that information.
While active but awaiting the first result, telemetry shows WAIT COMMS | Reps: 0.
An accepted zero is a valid first result and changes status to COUNTING.
Standby telemetry hides reps (Reps: --); REPS/STATUS can still inspect the last
stored total. A command acknowledgement is emitted even if sensor reads fail;
periodic telemetry still depends on successful sensor sampling.

MESSAGE CONTRACT

  REPS:<boot>:<session>:<total>

boot and session are unsigned decimal 32-bit HW-issued values. total is an
unsigned decimal integer from 0 to 2147483647. Extra fields, negative values,
non-digits, and values beyond uint32 are rejected as syntax errors. The command
must fit the existing 127-character line limit. No JSON or binary decoder is
provided. This is a new protocol; the comms teammate must implement its sender.

The ticket is separate from STREAM coordinator/session IDs. Obtain it AFTER
activation completes. Activation, RESET, a different exercise, or an actual mode
change clears the total and issues a new session. Repeating ACTIVATE on an active
board, selecting the same exercise/mode, or reconnecting Bluetooth preserves it.
Boot creates a fresh random boot identifier. STANDBY or handover stops acceptance;
reactivation issues a new session. A new set must use RESET and the new ticket.

Comms must associate each in-flight AR result with the ticket of the set that
produced it. Discard old inference results on reset/change; do not relabel an old
result with the new ticket. The count message does not select an exercise or
activate a board. PAUSE/CONTINUOUS remain mode metadata/sync controls and cannot
enable local counting; changing mode still resets the set for compatibility.

Results in REPS ACK:
  ACCEPTED       Valid first result or increasing cumulative total; stored.
  DUPLICATE      Same total as last accepted result; no extra count or flash.
  DECREASING     Lower total in the same session; ignored.
  STALE_SESSION  boot/session does not match the current ticket; ignored.
  INACTIVE       Board is standby, activating, or activation failed; ignored.
  OUT_OF_RANGE   total is greater than 2147483647; ignored.

ACK echoes the submitted ticket/total, even when rejected. REPS/STATUS returns
the actual stored state. Invalid syntax returns ERROR: Use REPS... rather than
an ACK. Retry the same total/ticket if an ACK is lost; retries are idempotent.
There is no spontaneous retry from HW. A downward correction requires a new set
(RESET), not a smaller value within the old session.

FEEDBACK

Each accepted increase flashes the active board and sends one mirrored LED event
to the peer using the existing ESP-NOW session. An increase from 2 to 5 sets 5
and flashes once; it does not replay three flashes. Duplicate/zero/rejected
messages do not flash. LED duration is 200 ms; closely spaced updates can extend
the lit interval. Mirrored events remain best effort; a lost LED packet cannot
change the stored total. Counts themselves are not forwarded between boards.

CODE LOCATIONS

  ExerciseNode.cpp: processCommand parses REPS, receiveRepCount applies it and
    emits ACK/feedback, restartSession changes the ticket, makeTelemetry displays
    the comms total. reportCommsReps prints the current ticket/state.
  CommsRepCounter.h/.cpp: ticket, total, and validation state without hardware IO.
  WirelessStreamer.cpp: existing USB/Bluetooth framing and comms telemetry text.
  LocalRepCounting.h/.cpp: retained local counting orchestration, bench-only.
  RepCounter.cpp / ContinuousCounter.cpp: retained local algorithms, bench-only.

A future in-process comms adapter can call ExerciseNode::receiveRepCount from the
same main loop as update(), using the current ticket. Never call it from a radio
callback; queue messages first. Its validation/ACK/feedback matches the command.

VALIDATION

exercise_node_startup_test.cpp covers both board roles, USB/Bluetooth input,
duplicates, malformed/stale/out-of-range/decreasing results, reconnect, standby,
activation failure, reset/exercise/mode/reboot changes, count/LED feedback, and
movement not counting. Existing sensor/stream regression checks remain there.
local_rep_counting_test.cpp checks the extracted local algorithms in isolation.
Host tests cannot establish real Bluetooth/ESP-NOW delivery or AR accuracy.
